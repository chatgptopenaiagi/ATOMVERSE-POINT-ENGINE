# Android feasibility and measured execution

The workstation has operational Android SDK platforms 35, 36, 36.1 and 37, build-tools 36.0.0, NDK r28c and r30, Gradle 9.3.1, Android Studio's JBR 25 and Flutter 3.47.8. NDK Clang 19 executes on the host. Chaquopy 17.2 and its CPython 3.14 ARM64 runtime were already cached. No model or duplicate desktop Python runtime was installed.

The original connected emulator advertised `x86_64,arm64-v8a` with `libndk_translation.so`, then disconnected. Verification therefore uses a separate project-local AVD created from the existing API 37 Google Play x86_64 image. Its private data directory and process are owned by this mission. No other project's emulator data was modified. This is compatible-emulator verification of the actual ARM64-only APK; no physical ARM64 device was available or claimed.

The Qt Android deployment tool currently requires a Unix host. The project instead uses native Android Java controls and a Canvas projection with Chaquopy embedding the original Python package. Gradle 9.3.1, Android Gradle Plugin 9.1.0 and Chaquopy 17.2 build a signed `arm64-v8a` APK with minSdk 24 and targetSdk 36. The kernel, command validation, oscillator, trajectories, runtime and SQLite history are reused directly. Only rendering, command widgets, lifecycle and checkpoint storage are platform adapters.

The native interface implements one entity, absolute/relative movement, radius/color, oscillators, line/helix paths, five views and local replay. No desktop Qt/OpenGL bindings, NVIDIA libraries, SQL ODBC driver or language model is required. Android AI, SQL replication and hardware modulation are not included. The mathematical kernel still implements its full validated command set, independently of which controls the initial touch interface exposes.

Acceptance installs the signed APK, launches it, invokes native widgets, sends actual ADB touch and camera gestures, checks background/foreground ticks, closes the activity, reopens the checkpoint and checks SQLite integrity and session preservation. Eight mathematical scenarios are compared against the packaged Windows executable with absolute/relative tolerance `1e-10`. The first replay check exposed a verification timing error: asynchronous loading completed after a fixed-delay assertion. The test now waits for completion with a bounded deadline. The live clock also prevents UIAutomator's idle-based hierarchy refresh; transport taps use coordinates inspected in the real 1080×2400 framebuffer, with state reports verifying their effects.

See [execution evidence](../EVIDENCE/MISSION-003-ANDROID.json), [initial failure](../EVIDENCE/MISSION-003-ANDROID-ITERATION.json) and [screenshot](../EVIDENCE/MISSION-003-ANDROID.png). Emulator startup and native translation affect measured timings; they are not physical-device performance estimates. Other Android API levels and devices are NOT TESTED.
